# 核心行为、所有权与生命周期契约

[English](CONTRACTS.md) · [返回首页](../README.zh-CN.md) · [入门教程](USAGE.zh-CN.md)

当你在代码中遇到**“调用失败或超时后，哪些指针仍然有效、哪些资源必须保留重试、哪些可以立即释放”**时，请查阅本页。如果是初次上手，建议先阅读 [常用任务教程](USAGE.zh-CN.md) 跑通第一个程序。

核心原则可以概括为一句话：**先检查 `hx_os_status` 状态码，再核对实际完成的字节数或进度，最后根据后台工作是否已彻底停止来决定是立即释放资源还是保留句柄等待重试。**

---

## 1. 错误状态、所有权与分配器上下文（`hx_os_context`）

### 1.1 状态码分类（`hx_os_status` 不是布尔值）

- **成功与非错误流状态（`>= 0`）**：
  - `HX_OS_OK`（`0`）：操作完成。
  - `HX_OS_EOF`（`1`）：已到达文件、流或目录枚举末尾。
  - `HX_OS_NEED_INPUT`（`2`）：流式解码/解析需要补充更多输入字节。
  - `HX_OS_OUTPUT_FULL`（`3`）：输出缓冲区容量不足，需扩容后重试。
- **错误、超时与阻塞状态（`< 0`）**：
  - 负值明确区分参数非法（`HX_OS_INVALID`）、内存不足（`HX_OS_NO_MEMORY`）、超时（`HX_OS_TIMEOUT`）、已取消（`HX_OS_CANCELLED`）、资源忙碌（`HX_OS_BUSY`）、暂时阻塞（`HX_OS_WOULD_BLOCK`）与超出上限（`HX_OS_LIMIT`）等。
  - 发生部分读写（Partial I/O）时，务必检查输出参数返回的实际已处理字节数。
- **独立错误详情（`hx_os_error`）**：
  - 本库不维护类似 `errno` 或 `GetLastError()` 的可变线程全局错误状态，也不会在内部偷偷调用日志回调。调用方可按需传入 `hx_os_error *` 接收统一状态码、底层错误域（如 `HX_OS_ERROR_WIN32`、`HX_OS_ERROR_ERRNO`、`HX_OS_ERROR_OPENSSL`）、原生错误码与次级原因码，并通过 `hx_os_error_message()` 格式化为 UTF-8 文本。

### 1.2 句柄所有权与“创建失败但保留 `owner`”的例外契约

除非头文件另有说明：
- **输入指针**：仅在函数调用期间被借用（Borrowed）。
- **输出对象**：由调用方独占持有（Owned），必须通过创建该对象的同一个库实例及配套销毁函数释放（严禁直接调用系统 `free()` 或跨不同插件的私有静态库副本混用释放）。销毁对象前，调用方必须确保没有新的并发调用进入。
- **模块裁剪与空指针清理**：已关闭模块的构造函数统一返回 `HX_OS_NOT_SUPPORTED`；文档标明支持 `NULL` 的销毁函数在收到 `NULL` 时安全执行空操作。

> [!WARNING]
> **创建/打开失败时仍需检查 `owner` 是否非空的 6 类对象**：
> 普通对象在创建失败时总是将输出指针置为 `NULL`。但下方表格中的 6 类含后台线程或系统句柄的对象，如果在**创建中途失败且内部回滚清理也未能立即完成**，会返回错误状态码，同时**保留非空的 `owner` 指针**（避免后台线程仍在运行时强行释放内存）。
>
> 遇到这种情况时，该 `owner` **仅可用于后续清理，不可用于业务操作**。请保留该 `owner` 及其关联的 `hx_os_context`，并调用下表对应的关闭接口重试清理：
>
> | 保留非空 `owner` 的对象类型 | 重试清理应调用的接口 |
> | --- | --- |
> | **线程池（Thread Pool）** | `hx_os_thread_pool_shutdown()`（C++：`hx::ThreadPool(owner).shutdownUntil(deadline)`） |
> | **协程运行时（Coroutine Runtime）** | 先调 `hx_os_coro_runtime_close_until()`，成功后再调 `hx_os_coro_runtime_destroy()` |
> | **目录监听（Directory Watch）** | `hx_os_watch_close_until()`（创建失败不会转移回调与 `cleanup` 的所有权） |
> | **协程 HTTP 服务（Coroutine HTTP）** | 先调 `hx_os_coro_http_close_until()`，成功后再释放其依赖的协程 `runtime` |
> | **子进程输出捕获（Process Capture）** | 在创建该对象的同一线程上调用 `hx_os_process_capture_close_until()` |
> | **命名共享内存（Shared Memory）** | `hx_os_shared_memory_close()`（未创建成功时 `data` 为 `NULL`、`size` 为 `0`） |

### 1.3 内存分配器上下文（`hx_os_context`）与 `Variant`

- **默认上下文（`NULL`）**：传入 `NULL` 上下文时，默认使用不可变的系统 `malloc` / `free` 策略。状态查询、能力位、时钟、Unicode 与原子操作无需任何上下文初始化。
- **自定义分配器上下文**：通过 `hx_os_context_create()` 创建显式上下文时会拷贝 `hx_os_allocator` 函数表并借用 `user` 指针（创建后不可中途更换）。分配器回调必须满足基础对齐要求、线程安全且支持跨线程释放；库包装层在此基础上提供更高阶的二次幂对齐，并在每块内存头部记录所属分配器。
- **上下文销毁边界**：只要还有关联对象或内存尚未释放（注意：即使是一个空的 `hx_string`，只要绑定了显式 `context`，也会持有该上下文的租约），调用 `hx_os_context_destroy()` 就会返回 `HX_OS_BUSY`。销毁上下文前必须先停止新内存分配并释放全部关联对象。
- **[Variant 动态值](VARIANT.zh-CN.md)**：同样遵循上述所有权规则。调用 `clear` 仅释放当前保存的值但仍保留对 `context` 的引用；调用 `destroy` 才会彻底释放对 `context` 的持有。自定义类型描述符与回调代码需保持有效，直至所有关联的 `Variant` 销毁完毕。

## 2. 时钟、截止时间（Deadline）与线程同步

### 2.1 单调时钟与截止时间语义

- **绝对单调截止时间**：所有带超时等待的接口均接收纳秒级绝对单调截止时间 `hx_os_deadline`，通常通过 `hx_os_deadline_after_ms(milliseconds)` 构造。
  - `HX_OS_DEADLINE_NOW`（`0`）：仅非阻塞轮询一次，不休眠等待。
  - `HX_OS_DEADLINE_INFINITE`（`UINT64_MAX`）：无限期等待（注意：`hx_os_sleep_until(HX_OS_DEADLINE_INFINITE)` 属于非法调用，返回 `HX_OS_INVALID`）。
- **时钟源特征**：单调时钟（Monotonic Clock）不包含系统休眠（Suspend）时间（Windows 下使用 `QueryUnbiasedInterruptTime`）；墙上时钟（Wall Clock）为 Unix 纪元毫秒数，可能随系统校时发生跳变。以纳秒为单位是为了统一表示范围，不承诺硬件具备纳秒级唤醒精度。
- **时钟读取错误处理**：带状态码的 `hx_os_monotonic_read()` / `hx_os_wall_time_read()` 会保留底层失败原因；便捷函数在底层时钟故障时分别返回 `UINT64_MAX` 或 `INT64_MIN`，此时构造出的截止时间会自动退化为 `HX_OS_DEADLINE_NOW`（立即失败退出，绝不因无效时钟而无限卡死）。

### 2.2 同步原语与线程生命周期保证

| 同步设施 | 核心行为与生命周期契约 |
| --- | --- |
| **互斥锁（Mutex）** | 默认非递归（可通过选项显式开启递归锁）；不保证先来先得的唤醒公平性 |
| **条件变量（Condition）** | 必须配合仅加锁一次的非递归互斥锁使用；无等待者时的 `notify` 通知不会被保留 |
| **条件等待（Cond Wait）** | 允许虚假唤醒（Spurious Wakeup），必须在 `while` 循环中检查业务谓词；返回时仍持有互斥锁 |
| **自动复位事件（Auto Event）** | 最多保留一次就绪信号，唤醒一个等待线程后自动复位为未就绪 |
| **手动复位事件（Manual Event）** | 触发后保持就绪状态并唤醒所有等待线程，直到调用方显式调用 `reset` |
| **线程汇合（Thread Join）** | 同一时刻仅允许一个调用者 `join`；等待超时（`HX_OS_TIMEOUT`）后可安全重试；`join` 成功即包含底层 TLS 析构完成 |
| **线程销毁（Thread Destroy）** | 在 `join` 成功前调用销毁会返回 `HX_OS_BUSY`；本库绝不执行非受控 `detach` 或强杀线程 |
| **线程局部存储（TLS Key）** | 线程正常退出时自动运行析构回调；若仍有线程持有非空 TLS 值，销毁该 Key 会返回 `HX_OS_BUSY` |
| **TLS 值更新与清理** | 重新 `set` 覆盖旧值时**不会**自动触发旧值的析构回调；显式调用 `clear` 或线程退出时才会调用析构回调 |

> [!NOTE]
> - 销毁互斥锁、条件变量或事件对象前，必须确保所有等待线程均已退出；等待超时不会破坏同步对象本身的有效性。
> - Windows 下使用光纤局部存储（FLS）实现线程退出時的 TLS 析构清理；如果宿主程序显式切换了原生 Win32 Fiber，该存储将表现为 Fiber 局部存储。
> - **原子操作（Atomics）**：提供 64 位整数与指针的对齐存储，发布给其他线程前必须先完成初始化，严禁将其放入 `packed` 或未对齐的结构体中，也不可在并发期间直接读写结构体内部字段。

## 3. 文件、路径与字符编码转换

### 3.1 文件读写与持久化边界

- **无额外用户态缓冲**：`hx_os_file` 直接封装操作系统原生文件句柄，不在库内维护类似 `FILE*` 的用户态缓冲区（内核页缓存依然存在）。
- **读写返回值契约**：
  - `read_some`：读到正数个字节时返回 `HX_OS_OK`；到达文件末尾且读到 0 字节时返回 `HX_OS_EOF`；请求读取 0 字节时直接返回 `HX_OS_OK`（不能用 0 字节读取来探测 `EOF`）。
  - `write_some` / `write_all`：`write_some` 可能只写入前缀部分字节；`write_all` 会循环推进写入并在中途失败时返回累计已写入字节数（调用方重试时只需发送剩余未写入的尾部数据）。
- **刷盘与关闭**：`sync` 通过 `fsync` / `FlushFileBuffers` 请求操作系统将修改刷入存储介质。`close` 无论底层是否报错都会消费并清空文件句柄指针（防止对已被系统复用的文件描述符重复 `close`）。

### 3.2 UTF-8 路径、目录遍历与字符串

- **统一 UTF-8 路径**：所有路径参数均为 `\0` 结尾的 UTF-8 字符串（Windows 内部自动转换为 UTF-16 并处理长路径前缀）。库不会隐式对路径做 Unicode 规范化、大小写折叠或跨文件系统拷贝移动（`rename` 跨分区时直接返回 `HX_OS_CROSS_DEVICE`）。
- **目录枚举**：每次读取拷贝 `\0` 结尾的文件名，`required` 包含末尾 `\0`；缓冲区不足返回 `HX_OS_OUTPUT_FULL` 时会保留当前目录项以便扩容后重试；枚举结束返回 `HX_OS_EOF`。
- **`hx_string` 与视图（`hx_string_view`）**：`hx_string` 保证内部始终为合法 UTF-8 且不可浅拷贝结构体；`hx_string_view` 仅借用字符内存，不可跨越原字符串的修改或销毁期使用。

### 3.3 流式字符编码转换（`hx_os_text`）

- 即使源或目标为 UTF-16 / UTF-32，输入与输出长度也**一律按字节（Bytes）计算**，且不隐式插入、剥离或猜测 BOM。
- `HX_OS_TEXT_STRICT` 遇到非法序列立即报错停止；`HX_OS_TEXT_REPLACE` 使用 `U+FFFD`（或 ASCII `'?'`）替换非法序列并统计替换次数。
- 返回 `HX_OS_OUTPUT_FULL` 时，只需扩容输出缓冲区并重新提交未消费完的输入；返回 `HX_OS_NEED_INPUT` 时，需保留未消费完的尾部字节并与下一块输入拼接后再次提交。

## 4. 内存池与线程池生命周期

- **有界内存池（Memory Pools）**：`maximum_bytes = 0` 表示允许按需增长；设置有限上限时，上限涵盖池向上游申请的内存块、分配包装头与元数据，`cached_bytes` 则单独限制空闲整块缓存的字节数。仍有未归还的活跃内存块时，销毁内存池返回 `HX_OS_BUSY`。Arena 分配器由调用方保证单线程/串行访问，调用 `reset` 会使此前从该 Arena 分配的所有指针一次性失效。
- **线程池（Thread Pool）**：固定工作线程数与等待队列容量（默认 2 个线程、256 个排队槽位）。提交被拒绝时不会接管调用方的 `user` 数据；一旦任务被池接受（包括随后在队列中被取消的任务），其 `cleanup` 回调保证在工作线程上恰好执行一次。
- **死锁保护**：在同一个线程池的工作线程内部同步等待该池尚未完成的任务或关闭该池，会立即返回 `HX_OS_DEADLOCK`。

## 5. 网络套接字与异步事件循环（Event Loop）

### 5.1 套接字属性与关闭契约

- **非阻塞与禁止句柄继承**：所有基础套接字默认均为非阻塞且不可被子进程继承（Windows 使用 `WSA_FLAG_NO_HANDLE_INHERIT`，Linux/Android 使用 `SOCK_CLOEXEC | SOCK_NONBLOCK` 及 `accept4`）。
- **关闭套接字后务必同时检查状态码与 `owner` 指针**：
  - **Windows**：若非阻塞套接字设置了非零 `SO_LINGER`，底层 `closesocket` 可能返回 `HX_OS_WOULD_BLOCK`。此时库会保留 `socket` 句柄、网络引用与事件循环绑定，调用方必须保留 `owner` 并在稍后重试关闭。
  - **POSIX（Linux / macOS / Android）**：底层 `close()` 只会调用一次；即使返回错误，文件描述符也已被内核回收且 `owner` 被置空，切勿拿旧描述符重复关闭。

### 5.2 事件循环线程归属与退出顺序

- **单驱动线程归属**：创建事件循环（`hx_os_loop`）的线程负责驱动循环（`run_until` / `poll_until`）、提交 I/O、附着套接字以及最终销毁循环；而 `POST` 跨线程投递、请求取消、引用计数增减与请求等待（`wait`）则支持跨线程安全调用。
- **回调契约**：已接受的异步请求保证在事件循环驱动线程上恰好执行一次完成回调（不在 `submit` 调用栈内同步重入，也不持有内部锁）。回调必须正常返回，严禁抛出 C++ 异常、调用 `longjmp` 或在回调执行期间卸载动态库。
- **安全关闭顺序**：调用 `hx_os_loop_close_until()` 会停止接收新请求、向在途请求发起取消并驱动它们完成退出（若超时返回 `HX_OS_TIMEOUT`，则所有活跃请求及其借用的缓冲区必须继续保留）。**待所有请求退出后，先关闭附着在该循环上的套接字，最后再调用 `hx_os_loop_destroy()` 销毁已关闭的事件循环。**

## 6. 动态库链接与插件安全卸载清单

无论是静态链接还是动态链接，对象都必须由创建它的同一个 `hx_c_platform` 实例释放。如果宿主程序支持动态加载/卸载业务插件（DLL / `.so`），在卸载插件前必须按顺序完成以下清理步骤：

1. **停止新任务准入**（不再向线程池、事件循环或信号处理器提交新请求）。
2. **等待所有后台任务、定时器与异步 I/O 回调彻底返回**（注意：只要有任何一项等待返回 `HX_OS_TIMEOUT`，说明后台线程仍可能跳入插件代码或访问插件内存，此时**严禁卸载插件**）。
3. **`join` 插件创建的所有工作线程**（确保线程退出且原生 TLS 析构回调执行完毕），并清空/销毁插件注册的 TLS Key。
4. **释放所有业务对象句柄，最后销毁插件专属的 `hx_os_context`**（确认返回 `HX_OS_OK` 而非 `HX_OS_BUSY`）。
5. **关于 `fork()` 与异步信号**：在 POSIX 系统上 `fork()` 出的子进程不可直接复用父进程已创建的同步原语、线程池或事件循环（子进程应直接 `exec` 或在全新环境中初始化）；库内所有接口均不承诺异步信号安全（Async-Signal-Safe）。
